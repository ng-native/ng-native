Every service's `available` is a `Signal<boolean>`, read as `available()`, in `@ng-native/device`, `@ng-native/expo`, `@ng-native/firebase-messaging` and `@ng-native/nativescript`. `DevMenu`, `Haptics`, `SplashScreen`, `Tracking`, `Fonts` and `Watch` had it as a property, and `Biometrics`, `AppleSignIn`, `ScreenCapture` and `StoreReview` as a method that resolved: those are false until the platform answers, a turn after the first read, and `Biometrics` asks again each time the app comes back to the front. A sensor's `available()` is `false` until the platform answers, where it was `null`. The services that had no `available` gain one: `HardwareBack` and `NavigationBar` are available on Android, `StatusBar` and `Keyboard` on iOS and Android, and `Vibration` on iOS and Android. These services, where absent, now answer their return type's empty value rather than throwing: `FileSystem` on the web and in a test that provides no module hands back a file that is not there and `pickDirectory()` answers `null`, while a build missing the module on iOS, Android or macOS still throws a `MissingModuleError` when it is used; and `TextRecognition.recognize()` answers no text on Android and the web. The `available-signal` migration rewrites the reads and the awaits it can trace to a service, through `inject()`, a field or a variable initialised with one, or a type, and notes some of what it cannot, such as a namespace import or a promise still used as one. A read through a name it cannot trace, such as an untyped alias, is left as it is without a note, so check what it leaves; see [Updating an app](https://ng-native.com/guide/updating) for how to run it. `@ng-native/eslint-plugin`'s new `no-uncalled-available` rule, on in `recommended`, reports `available` read as a condition without calling it in TypeScript, not in templates, and `eslint --fix` adds the call where it is read off an `@ng-native` service it can identify; elsewhere the call is offered as a suggestion.
