## 0.28.0 (2026-11-24)

### 🚀 Features

- Queries leave out what a tab behind the selected one in a `<native-tabs-outlet>` holds, as the tab bar shows only the selected tab, so a test that found content on a tab behind no longer finds it. ([#1806](https://github.com/ng-native/ng-native/pull/1806), [#1783](https://github.com/ng-native/ng-native/issues/1783))

  To migrate, select the tab first, or pass `{ includeHiddenElements: true }` to a query that means to reach a tab behind.

  The `<native-tab>` itself, its item in the bar, is still found. A query `within` a view on a tab behind finds nothing either.

- Queries leave out the screens of a native stack that a pushed screen covers, as React Native Testing Library leaves out what is hidden from accessibility, so a test that found content on a screen below the top no longer finds it. ([#1780](https://github.com/ng-native/ng-native/pull/1780), [#1767](https://github.com/ng-native/ng-native/issues/1767), [#1769](https://github.com/ng-native/ng-native/issues/1769), [#1752](https://github.com/ng-native/ng-native/issues/1752))

  To migrate, query what is on the screen in front, or pass `{ includeHiddenElements: true }` to a query that means to reach a screen below it.

  A screen under a push, a `fullScreenModal` or a `containedModal` is hidden, and on Android a screen under a `modal` (what `present()` shows by default) or a `pageSheet` too, which Android shows full screen. Everything on a hidden screen is hidden, `within` included, whether it starts from the screen or from a view on it, and so is what is `within` a view under one hidden from accessibility. A screen under a sheet or a transparent modal is still showing, and still found, and so is one under a `modal` or a `pageSheet` on iOS.


### 🩹 Fixes

- A bound style ending in `!important`, `[style.width]="'10px !important'"`, is now read as its value. Before, Angular left a space where it took `!important` off, and the value reached native as the text `'10px '`, which it dropped. A bound style set to an empty string, `[style.width]="''"`, now takes the declaration out, as a browser does, so a class rule for it applies again. Before, the empty value stayed in the inline style. A bound style that is only whitespace, other than a custom property, is dropped and the value it had is kept, as Chrome does, with a warning in development. A custom property bound to whitespace keeps a blank value that hides one of the same name from a class, as Chrome's `--h: ;` does. ([#1445](https://github.com/ng-native/ng-native/pull/1445))
- `userEvent.press`, `userEvent.longPress` and `fireEvent.press` on a `<ui-toggle>` flip it, as a tap does on iOS, Android and macOS, where before they did nothing. ([#1806](https://github.com/ng-native/ng-native/pull/1806), [#1783](https://github.com/ng-native/ng-native/issues/1783))

  On iOS and macOS the press ends with SwiftUI's `isOnChange`, the opposite of the bound `isOn`, or with none bound, of what the last press switched it to; one SwiftUI's `disabled` modifier turns off sends none. On Android it ends with Compose's `checkedChange`, the opposite of the value the switch shows. Either way `(isOnChange)` runs.

- `userEvent.press`, `userEvent.longPress` and `fireEvent.press` on a `<switch>` flip it, as a tap does on iOS, Android and macOS, where before they did nothing. ([#1780](https://github.com/ng-native/ng-native/pull/1780), [#1767](https://github.com/ng-native/ng-native/issues/1767), [#1769](https://github.com/ng-native/ng-native/issues/1769), [#1752](https://github.com/ng-native/ng-native/issues/1752))

  The press ends with the `change` event the native switch sends, with the opposite of the value last committed, so `(checkedChange)`, `[(checked)]` and a form field see the new value. A disabled switch sends none. `fireEvent(node, 'change', { value })` sets a given value.

- The Vitest plugin compiles a component's stylesheet for the `os` it runs as, so a test checks CSS against that OS alone, as Metro does for the platform it bundles. ([#1780](https://github.com/ng-native/ng-native/pull/1780), [#1767](https://github.com/ng-native/ng-native/issues/1767), [#1769](https://github.com/ng-native/ng-native/issues/1769), [#1752](https://github.com/ng-native/ng-native/issues/1752))

  On macOS, Linux and Android a `filter` such as `grayscale(1)` is kept, where before it was dropped with the iOS warning, and an iOS project keeps a `skewX()`, which only Android refuses. A `web` project's stylesheets are compiled for iOS and Android together, as before. The warnings a test run prints change to match.

- `userEvent.press`, `userEvent.longPress`, `userEvent.type`, `userEvent.clear` and `fireEvent.press` do nothing on a screen nobody can see, a native stack screen another covers or a tab behind the selected one, where before they reached a node found there with `includeHiddenElements`. A `userEvent.press` or `userEvent.longPress` whose screen goes out of sight while the finger is down ends in a cancelled touch, with no press. ([#1806](https://github.com/ng-native/ng-native/pull/1806), [#1783](https://github.com/ng-native/ng-native/issues/1783))

  Content of an `@expo/ui` sheet or popover presented from such a screen still takes a press, as it shows in a window of its own. A node hidden only from accessibility still takes a press, as React Native Testing Library presses it.

- On macOS and Linux, `<sidebar-item>`, `<native-button>` and a desktop `<native-tab>` take an icon's SVG markup, such as an `@ng-icons` icon, as their icon: `[icon]="{ svg: lucideBlocks }"`. ([#1804](https://github.com/ng-native/ng-native/pull/1804), [#1756](https://github.com/ng-native/ng-native/issues/1756))

  `ButtonIcon` has a third form, `{ svg: string }`, which the desktop host draws as its own icon: on macOS a template image AppKit tints for the selection, an inactive window and Increase Contrast, as it does an SF Symbol, and on Linux in the row's or the button's text colour. On macOS and Linux `<sidebar-item>` and `<native-button>` commit it as the `svgIcon` prop, and on macOS an `sfSymbol` set beside it wins.

  A `<native-tab [icon]="{ svg }">` on macOS and Linux needs no `withSvgIcons` renderer, and commits its markup as a `data:image/svg+xml` icon source, which the host draws as the icon of the tab's sidebar row.

  iOS, Android and the web draw no SVG button icon, and in development a `<native-button>` says so once. Either element also says once when its markup is no `<svg>` element, such as an icon's name given in its place.

- A `<sidebar-item>` with a `path` that an `@for` or an `@if` renders no longer throws NG0950 at launch, and the route selects it as it does a static one. ([#1777](https://github.com/ng-native/ng-native/pull/1777), [#1750](https://github.com/ng-native/ng-native/issues/1750), [#1755](https://github.com/ng-native/ng-native/issues/1755), [#1757](https://github.com/ng-native/ng-native/issues/1757), [#1758](https://github.com/ng-native/ng-native/issues/1758))
- A `shortcut` on `F13` to `F20` now fires from a key press on macOS, Linux and, with a modifier as every Android shortcut needs, Android 16 and later, where before only a macOS menu item could use those keys. ([#1809](https://github.com/ng-native/ng-native/pull/1809), [#1798](https://github.com/ng-native/ng-native/issues/1798), [#1786](https://github.com/ng-native/ng-native/issues/1786))

  The macOS and Linux hosts now name those keys in their key events, and the Linux menu bar shows them as accelerators. On Android, `F13` to `F20` have key codes from Android 16 (API 36), where the Keyboard Shortcuts helper lists them by key code; an older Android's helper leaves them out. iOS still stops at `F12`, as UIKit names no key past it.

- A `repeating-linear-gradient(...)` in a stylesheet now compiles to the tile that draws the same stripes, one linear gradient with `background-size` and `background-repeat`, where it used to be dropped with a build warning. ([#1782](https://github.com/ng-native/ng-native/pull/1782), [#1770](https://github.com/ng-native/ng-native/issues/1770), [#1774](https://github.com/ng-native/ng-native/issues/1774))

  The lowering takes stops in `px` or `rem`, the first at 0 or with no position and the last with one, and a direction that is an angle or a side, on iOS, Android, macOS and Linux. Percentage, `em` and viewport stops, a first stop not at 0, a corner direction, and a `background-size` or a `background-position` in lengths written beside it in the `background` shorthand are still dropped with a build warning, which now names the tile to write instead. A `var()` in a repeating gradient, a token holding one, and `repeating-radial-gradient` are dropped with a warning as before. The tile sets that layer's background size, position and repeat.

  The build error for a component whose `styles` or `host` is imported from another file now says what to write instead: a `.css` file in `styleUrl` or `styleUrls` for styles, and bindings in the same file or a directive in `hostDirectives` for a host.

- A `repeating-linear-gradient(...)` along a side with percentage stops now compiles to a tile that percentage of the box, a period in `px` or `rem` under 1px is dropped with a build warning, and an ordinary background image that wins over a repeating gradient no longer takes the tile's size, position and repeat. ([#1815](https://github.com/ng-native/ng-native/pull/1815), [#1785](https://github.com/ng-native/ng-native/issues/1785))

  Percentage stops are lowered only along a side (`to bottom`, `to right`, `90deg` and the like) and only when every positioned stop is a percentage or 0; at any other angle, or mixed with `px` or `rem` stops, they are still dropped with a warning. A repeating gradient's `background-image` written after a `background-size`, or a `background-position` in lengths, in the same rule is now dropped with a warning, as it already was beside them in the `background` shorthand, where its tile used to replace the author's placement. A period in `px` or `rem` under 1px is dropped with a build warning: Chrome paints whichever stripe each device pixel lands on rather than their average color, so no tile matches it. The tile's placement now belongs to its image: where a stronger rule, an important declaration or the element's own style gives an ordinary `background-image`, that image is placed by what a weaker rule set or what was written after the tile, as in a browser, where it used to keep the tile's placement.

- `<pressable [menu]>` opens a menu of `<menu-item>`s under the element on a press, instead of firing `(press)`: on macOS as an `NSMenu`, and on Linux as a popover menu. ([#1799](https://github.com/ng-native/ng-native/pull/1799), [#1765](https://github.com/ng-native/ng-native/issues/1765))

  A click, a screen reader's press or, on macOS, Space on the focused element opens it, and `PressMenu.open()` (`#menu="pressMenu"`) opens it from code. A menu of `[checked]` items is a pop-up select. iOS, Android, Expo Go and the web host draw no menu on a press yet: there a press fires `(press)`, with one warning in development. The desktop host's `NgNativeMenus` module has a new `popUpMenu(view, entries)` method for it. A `<menu-item>` with a one-way `[checked]` binding now stays as the app binds it when chosen, rather than toggling on its own, so a menu of choices keeps the one the app keeps checked; a two-way `[(checked)]` still toggles.

- A `<pressable [menu]>` now opens its menu on Android, as a PopupMenu below the element, on a tap, a TalkBack press, Space, Enter or the D-pad centre, and from `open()`, with checked items shown checked. ([#1817](https://github.com/ng-native/ng-native/pull/1817), [#1800](https://github.com/ng-native/ng-native/issues/1800))

  It takes the `NgNativeMenus` module's new `popUpMenu(view, entries)`, with the view's tag as on the desktop host, which a development build has and Expo Go does not; in Expo Go a press still fires `(press)`, with one warning in development. The module finds the view in whichever window it is in, so a pressable inside a `<modal>` opens its menu too. iOS still fires `(press)` with the warning.

- `nx sync:check` now says an app lacks a native module or its config plugin, rather than that a development build would not link the module, which holds only where the app imports a library through a path alias. ([#1723](https://github.com/ng-native/ng-native/pull/1723))

  Expo's autolinking walks the app's dependency tree. Where the app imports a library through a tsconfig path alias, as in an integrated workspace, a native module the library imports is linked only when the app lists it or another of the app's dependencies brings it in. Where the library is a workspace package the app lists, a native module in the library's `dependencies` or required `peerDependencies` is linked too. Either way, the sync generator adds the module to the app, where `expo install --check` checks its version, and its config plugin to `app.json`, which is where Expo applies it from, apart from the few plugins Expo applies itself. The Nx page says the same.

- `nx g @ng-native/nx:app` now writes an app that typechecks, resolves path aliases in tests without a warning and lints with the workspace's rules, and `desktop-only-events` no longer warns in an app that builds for no phone. ([#1778](https://github.com/ng-native/ng-native/pull/1778), [#1746](https://github.com/ng-native/ng-native/issues/1746), [#1747](https://github.com/ng-native/ng-native/issues/1747), [#1754](https://github.com/ng-native/ng-native/issues/1754), [#1761](https://github.com/ng-native/ng-native/issues/1761))

  - `@ng-native/eslint-plugin`'s `desktop-only-events` does not warn in a project whose `expo.platforms` lists no `ios` or `android`, such as a `--desktopOnly` app, where the event fires on every OS it builds for. It warns again once a phone is listed.

- `<ng-icon>` costs less on a screen with many of them, since a `color` or `size` bound on an icon with no text, no gradient and no paint from a CSS custom property now restyles and re-commits only the icon's own view. ([#1732](https://github.com/ng-native/ng-native/pull/1732))

  Before, a colour change restyled every shape in the icon and re-committed each one, and so did a size change on an icon with a colour bound. Across 1,000 outline icons in the Node bench, a colour change takes about 55% less JavaScript time, a size change about 50% less, and drawing them all about 25% less. The shapes of those icons no longer commit the text colour and font they inherited and never drew with: react-native-svg paints a `currentColor` shape from the drawing it is in.

  A markup is parsed once and shared by every icon that draws it, while it is among the 500 kept; past that the store is emptied and each markup parsed again when next drawn. Each of its elements is translated to native props once and reused by the icons drawn after it with the same stroke width, except a gradient, which reads the `color` input.

- `<ng-icon>` draws the shapes of an outline icon that can be drawn as one, next to each other with one stroke and no fill and under the conditions below, as a single native path, so a lucide icon commits half as many native views and a tabler, feather, iconoir or huge-icons icon a quarter to a third fewer. ([#1737](https://github.com/ng-native/ng-native/pull/1737))

  Shapes merge only where one path draws them as they were drawn apart, but for the one commit described below: next to each other, with no fill, no opacity, dash or marker, the same paint and not a gradient or pattern, no value from a CSS custom property other than ng-icons' stroke width, no `id` another element points at, path data and points that parse to their end, and no closed shape that is no wider or taller than its stroke at the stroke width the icon draws with. Where two strokes in a colour with any transparency cross, drawn apart the crossing is blended twice, as the web draws it, and drawn as one path it is blended once, which shows as a different shade. So `currentColor` shapes merge only while the icon's colour is opaque as far as `<ng-icon>` knows when it draws them: a colour on its `color` input is known from the commit that sets it, and a stylesheet's from the commit after the one that settles it. In the commit in which a stylesheet colour stops being opaque, the crossings are blended once, and from the next one the shapes are drawn apart: that commit is a new icon's first, where its own stylesheet colour is not opaque and its parent's is, or one that changes the colour of an icon already drawn, as a change of theme can. A stroke written in a colour of its own merges only where that colour is opaque. Every other shape is drawn as before. Across 1,000 lucide icons on the iOS simulator, drawing them takes about 10% less JavaScript time and 20% less main-thread time.

  Where two strokes cross, edge pixels blend once rather than twice, and on iOS a stroke edge that sits on a pixel boundary can round to the pixel beside it. Every ng-icons icon the merge changes was compared with its unmerged drawing on iOS and Android, with no shape moved or missing.

- A `<modal [anchor]>` bound to a template reference now type-checks under `strictTemplates`, `@ng-native/expo` exports `./date-time-picker` and `./segmented-control`, and a shortcut with a misspelt key name now throws. - A value set on an element that a browser drops and the engine recognises, such as `[style.width]` going from `40px` to `-4px` or `[style.padding]` to `1px -1px`, now leaves the value set before it, as Chrome's `setProperty` does, where it took that value away so the stylesheet's showed. ([#1391](https://github.com/ng-native/ng-native/pull/1391), [#1373](https://github.com/ng-native/ng-native/issues/1373))

  This holds for a single property, a shorthand of sides such as `padding`, with one value or several, and a shorthand of mixed parts such as `border` or `background`, and for a previous value that was a `var()`. The values recognised are a negative where a property has nothing below zero, math that comes to no type the property takes, an `aspect-ratio` that is no ratio, and a shorthand with more values than it takes or a part one of these. Other text a browser drops, such as `garbage`, still replaces the value, except on a shorthand of mixed parts such as `border` or `background`, which keeps the value before any text it cannot read. The dropped value is still reported with a warning in development. Removing the binding takes the earlier value away, as before. A `style` attribute set again is a new declaration block, as in a browser: a value it changes to one that is dropped leaves no value there, so the stylesheet's shows.

  In a keyframe, a `box-shadow` or a colour such as `background-color` in `currentColor`, written or as a token's fallback such as `var(--x, currentColor)`, which a frame refuses, now leaves the value the frame gave before it, as any other refused value does, where it took that value away, and a shorthand such as `outline` keeps all of its earlier parts. This holds where the refusal is reported as a warning, as the app's build reports it; `compileCss` called with no `onUnsupported` throws instead. A frame's `color: currentColor` no longer drops a later declaration with a value worked out on the device, such as `width: 1em`, nor is it dropped by one. In development, a `box-shadow` in `currentColor` where the colour in scope is a platform colour, such as `CanvasText` or `platform-color()`, including through an unset inset token as in Tailwind's ring, is now said to be dropped, where it was dropped with nothing said. This includes a shadow in a mix of `currentColor`, such as `color-mix(in srgb, var(--x) 50%, white)` where `--x` is `currentColor`, and a token holding a shadow, alone or in a list, such as `box-shadow: var(--shadow)` or `box-shadow: var(--shadow), 0 0 1px red`.
